# Доменная документация

Как скиллы должны читать доменную документацию этого репозитория, когда изучают
код.

## Перед изучением кода прочитать

- **`CONTEXT.md`** в корне репозитория, либо
- **`CONTEXT-MAP.md`** в корне, если он есть: этот файл указывает на отдельный
  `CONTEXT.md` для каждого контекста — читать те, что относятся к теме.
- **`docs/adr/`**: читать те ADR, которые касаются области предстоящей работы. В
  многоконтекстных репозиториях смотреть ещё и `src/<context>/docs/adr/` —
  решения уровня контекста.

Если чего-то из этого нет, **молча продолжать**. Не сообщать об отсутствии и не
предлагать создать заранее. Скилл `/domain-modeling` (к нему ведут
`/grill-with-docs` и `/improve-codebase-architecture`) создаёт эти файлы по
необходимости — когда термин или решение действительно нужно зафиксировать.

## Раскладка файлов

У этого репозитория **один контекст** — так и есть у большинства: пакет один,
`workspaces` не используются.

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-postgres-vezde.md
│   └── 0002-izolyaciya-runnera.md
└── src/
```

Многоконтекстная раскладка (признак — `CONTEXT-MAP.md` в корне) выглядела бы так,
и она здесь не используется:

```
/
├── CONTEXT-MAP.md
├── docs/adr/                          ← решения уровня системы
└── src/
    ├── runner/
    │   ├── CONTEXT.md
    │   └── docs/adr/                  ← решения уровня контекста
    └── auth/
        ├── CONTEXT.md
        └── docs/adr/
```

Пока `CONTEXT.md` и `docs/adr/` не появились, роль доменной документации играют
человеческие документы из оглавления README: `docs/auth.md`, `docs/runner.md`,
`docs/deployment.md`, `docs/legal.md`. Это не замена глоссарию, но там описано,
как устроены вход, песочница раннера и раскатка.

## Пользоваться словарём глоссария

Когда в выводе появляется доменное понятие (в заголовке задачи, в предложении по
рефакторингу, в гипотезе, в имени теста) — брать термин в том виде, как он
определён в `CONTEXT.md`. Не съезжать на синонимы, которых глоссарий избегает.

Если нужного понятия в глоссарии ещё нет — это сигнал: либо вы придумываете язык,
которого в проекте нет (стоит остановиться), либо это настоящий пробел (отметить
для `/domain-modeling`).

## Отмечать конфликты с ADR

Если вывод противоречит существующему ADR — сказать об этом прямо, а не
переписывать решение молча:

> _Противоречит ADR-0007 (изоляция раннера), но стоит пересмотреть, потому что…_

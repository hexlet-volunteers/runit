# Как участвовать в разработке

## С чего начать

Установка, запуск, тесты и миграции — в [README](README.md). Минимум, чтобы
начать: PostgreSQL из compose, `npm install`, `npm run dev`, фронтенд отдельно.

Задачи — в [issues](https://github.com/hexlet-volunteers/runit/issues). Если
берёте что-то в работу, напишите об этом в issue: так видно, что она занята.

Прежде чем предлагать крупное изменение, обсудите его в issue. Причина
практическая: у многих решений в проекте есть неочевидная предыстория, и она
записана в комментариях к коду, а не в документации.

## Стиль кода

Форматирование и линтер — Biome, `npm run lint:fix`. Правила в `biome.json`,
спорить с ними не нужно.

Главное правило проекта не про форматирование, а про комментарии: **комментарий
объясняет «почему», а не «что»**. Что делает код, видно из кода. В комментарий
идёт то, чего в коде не видно: какая альтернатива отвергнута и по какой причине,
какой сбой это предотвращает, что сломается, если сделать «очевидным» способом.

Как это выглядит — посмотрите `src/security.ts`, `src/config/env.ts` или
`bin/typeorm-to-drizzle.sql`. Такие комментарии — не украшение: почти каждый из
них описывает поломку, которая уже случалась на боевом стенде.

Комментарии и сообщения коммитов — на русском.

## Ветки и коммиты

Ветка — от `main`, имя вида `fix/database-ssl`, `feat/oembed`, `docs/contributing`.

Сообщения коммитов внутри ветки пишите по Conventional Commits, но помните: в
`main` они не попадут. При squash история ветки сворачивается в один коммит, и
его заголовок берётся из PR — см. ниже.

## Pull request

### Заголовок

Мержим squash, поэтому **заголовок PR становится сообщением коммита в `main`**.
Отсюда два следствия: он остаётся в истории навсегда, и по нему release-please
считает версию и собирает CHANGELOG.

Формат: `тип(подсистема): описание`. Описание на русском, с маленькой буквы, без
точки в конце.

| Тип | Когда | Что делает с версией |
| --- | --- | --- |
| `feat` | новое поведение | поднимает patch (см. про 0.x ниже) |
| `fix` | исправление | поднимает patch |
| `perf` | ускорение без смены поведения | поднимает patch |
| `revert` | откат прежнего изменения | поднимает patch |
| `chore` | обслуживание: зависимости, конфиги, документация | поднимает patch |
| `build` | сборка, Dockerfile, CI | поднимает patch |

Ломающее изменение — с восклицательным знаком: `feat!: убрать поддержку старых
ссылок`. Только оно поднимает мажорную версию.

### Подсистему пишут в scope, а не в тип

Набор типов закрытый — ровно шесть из таблицы. Всё остальное идёт в scope:

```
✅ fix(ci): проверка типов в тестах не видела объявлений *.d.ts
✅ chore(deps): обновить fastify до 5.8
✅ chore(docs): описать процесс выпуска
❌ ci: проверка типов в тестах не видела объявлений *.d.ts
❌ docs: описать процесс выпуска
❌ refactor: вынести раздачу статики в модуль
```

Причина не в педантизме. Типы `ci`, `docs`, `refactor`, `style` и `test`
формально допустимы в Conventional Commits, но в `release-please-config.json` их
нет — такой PR **молча** не попадёт ни в CHANGELOG, ни в версию. Ошибки не будет:
всё зелёное, изменение просто исчезает из истории выпусков.

Так что рефакторинг — это `chore(runner):`, документация — `chore(docs):`,
правка CI — `fix(ci)` или `chore(ci)`.

### Описание

Что изменилось, видно в diff. В описании — почему: какую проблему это решает,
какие варианты отвергнуты, что проверено и как. Номер issue: `Закрывает #941`.

## Проверки

На каждый PR запускаются четыре job'а из
[`.github/workflows/pull-request.yml`](.github/workflows/pull-request.yml), и все
четыре обязательны:

| Проверка | Что делает |
| --- | --- |
| Бэкенд — линтер, типы, тесты | Biome, `tsc` по двум конфигам, тесты против настоящей PostgreSQL, аудит прод-зависимостей |
| Фронтенд — тесты, типы, сборка | типы, vitest, сборка Vite, аудит прод-зависимостей |
| Раннер — исполнение 9 языков в Docker | собирает образы языков и реально прогоняет код, stdin, таймаут и изоляцию сети; проверяет, что контейнеры не осиротели |
| Сборка образов | образы бэкенда и фронтенда плюс `caddy validate` |

Проверок типов **две**: основная и `-p tsconfig.test.json`. Перед пушем
прогоняйте обе:

```bash
npm run lint && npx tsc --noEmit && npx tsc --noEmit -p tsconfig.test.json && npm test
```

Ошибка, проходящая мимо первой проверки типов и валящая вторую, уже случалась.

Ветка обязана быть свежей относительно `main` (`strict`). Это не формальность:
при squash коммит в `main` не равен голове ветки, и без требования свежести
зелёный PR проверял бы не то состояние, которое уедет в `main`. Если GitHub
просит обновить ветку — `git pull --rebase origin main`.

## Ревью

Ревью **не блокирует мерж, и это сделано намеренно**: автор мержит свой PR сам,
как только проверки зелёные. Ревью приходит после — на смерженный код.

Смысл в том, чтобы ревью не превращалось в узкое место. Замечания по уже
смерженному оформляются отдельной правкой или issue, а не задерживают доставку.

Из этого следует требование к описанию PR: оно пишется для того, кто придёт
читать код **позже**, а не для того, кто одобрит мерж сейчас. Если решение
неочевидно, его причина должна быть либо в комментарии к коду, либо в описании
PR — иначе ревьюер восстанавливает её по памяти автора, которой у него нет.

## Мерж и ограничения `main`

Мерж — **squash**. Один PR — один коммит в `main` — одна запись в CHANGELOG.

Мерж-коммит и rebase не подходят: они уносят в `main` все внутренние коммиты
ветки, и release-please прочитает каждый. В CHANGELOG попадут `wip` и
`поправил опечатку` — так уже было, в закрытом релизном PR #948 всплыли записи
вида `header start` из старой истории. Пока запрет остальных стратегий не
настроен (issue #951), выбирайте **Squash and merge** руками.

Что защищает `main`:

* четыре обязательные проверки — красный PR смержить нельзя;
* ветка обязана быть свежей (`strict`);
* force-push и удаление ветки запрещены.

Обход защиты администратором оставлен **включённым намеренно** — чтобы
протолкнуть хотфикс, когда боевой стенд лежит и ждать проверки некогда. Это
аварийный выход: в обычной работе прямой push в `main` не делают.

## Выпуск версии

Теги руками не ставят. `make release` и `git push heroku` не существуют.

Версию считает [release-please](https://github.com/googleapis/release-please). На
каждый пуш в `main` он обновляет **релизный PR** с заголовком вида
`chore(main): release 0.2.1`: там поднятая версия в `package.json` и дописанный
`CHANGELOG.md`. Пока PR открыт, ничего не выпущено — он копит изменения.

**Мерж релизного PR и есть выпуск.** Один и тот же прогон:

1. ставит тег `v0.2.1` и создаёт запись в GitHub Releases;
2. публикует образы приложения, фронтенда и девяти раннеров в GHCR;
3. раскатывает оба стенда — свой сервер и PaaS.

Отсюда следствие: **частота выпусков — это частота, с которой мержат релизный
PR.** Нужен релиз на каждую фичу — мержите сразу; раз в неделю — он накопится за
неделю и уедет одной версией.

### Версии до 1.0.0

Пока версия ниже `1.0.0`, `feat` поднимает patch, а не minor
(`bump-patch-for-minor-pre-major`) — так настроено в `hexlet-basics` и
`hexlet/hexlet`, здесь сделано так же. То есть `0.2.1`, `0.2.2`, `0.2.3`, пока
кто-нибудь осознанно не выпустит `1.0.0`.

## Когда что-то сломалось

**Проверки на PR красные.** Защита не даст смержить — это её работа. Правьте и
пушьте в ту же ветку.

**Упала раскатка после выпуска.** Тег и запись в Releases уже созданы,
переделывать выпуск не нужно. Перезапустите упавший job:

```bash
gh run rerun <id> --failed
```

**Не поднялся стенд.** Смотрите README, раздел
[«Развёртывание»](README.md#развёртывание). Учтите отдельно: откат кода в
одиночку может не помочь, если выпуск нёс миграцию базы — тогда нужен и откат
базы из бэкапа.

## Чего в этом процессе нет намеренно

**Блокирующего ревью** — см. раздел «Ревью» выше.

**Проверки заголовка PR.** Сейчас ничто не мешает открыть PR с заголовком не по
конвенции, и такое изменение молча не попадёт в CHANGELOG. Дыра известна и
описана в issue #951 вместе с тем, чем её закрыть.

**Дублирования проверок на push в `main`.** `push.yml` делает меньше, чем
`pull-request.yml`, и это нормально: изменения приходят через PR, строгость нужна
именно там.

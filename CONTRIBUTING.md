# Как участвовать в разработке

Про запуск, тесты и миграции — [README](README.md). Здесь только про то, как
изменения доезжают до `main` и как выпускается версия.

## Коротко

1. Ветка от `main`, изменения — только через pull request.
2. **Заголовок PR** пишется по Conventional Commits: `fix(runner): не падать на пустом вводе`.
3. Зелёные проверки — обязательны, красный PR смержить нельзя.
4. Мерж — **squash**.
5. Релиз — мерж релизного PR от release-please. Теги руками не ставят.

## Изменения попадают только через PR

`main` защищён: force-push и удаление ветки запрещены, четыре проверки
обязательны.

Обход защиты администратором оставлен включённым намеренно — чтобы протолкнуть
хотфикс, когда боевой стенд лежит и проверки ждать некогда. Это аварийный выход,
а не рабочий путь: в обычной работе прямой push в `main` не делают.

## Заголовок PR — это сообщение коммита

Мержим squash, поэтому в `main` попадает один коммит, и его заголовок берётся из
PR. Отсюда два следствия, которые важнее, чем кажется:

* заголовок PR читают не только в PR — он остаётся в истории `main` навсегда;
* по нему release-please считает версию и собирает CHANGELOG.

Формат: `тип(подсистема): описание`. Описание на русском, с маленькой буквы, без
точки в конце. Подсистема — необязательна, но полезна: `fix(runner):` понятнее,
чем просто `fix:`.

| Тип | Когда | Что делает с версией |
| --- | --- | --- |
| `feat` | новое поведение | поднимает patch (см. ниже про 0.x) |
| `fix` | исправление | поднимает patch |
| `perf` | ускорение без смены поведения | поднимает patch |
| `revert` | откат прежнего изменения | поднимает patch |
| `chore` | обслуживание: зависимости, конфиги, инфраструктура | поднимает patch |
| `build` | сборка, Dockerfile, CI | поднимает patch |

**Ломающее изменение** объявляется восклицательным знаком: `feat!: убрать
поддержку старых ссылок`. Только оно поднимает мажорную версию.

### Подсистему пишут в scope, а не в тип

Набор типов закрытый — ровно шесть из таблицы. Всё остальное идёт в scope:

```
✅ fix(ci): проверка типов в тестах не видела объявлений *.d.ts
✅ chore(deps): обновить fastify до 5.8
❌ ci: проверка типов в тестах не видела объявлений *.d.ts
❌ docs: описать процесс выпуска
❌ refactor: вынести раздачу статики в модуль
```

Причина не в педантизме. Типы `ci`, `docs`, `refactor`, `style` и `test`
формально допустимы в Conventional Commits, но в
`release-please-config.json` их нет — такой PR **молча** не попадёт ни в
CHANGELOG, ни в версию. Ошибки при этом не будет: всё зелёное, изменение просто
исчезает из истории выпусков.

Правило снимает эту ловушку: рефакторинг — это `chore(runner):`, документация —
`chore(docs):`, правка CI — `fix(ci)` или `chore(ci)`.

### В описании PR — почему, а не что

Что изменилось, видно в diff. В описании нужно то, чего в diff не видно: почему
так, какие варианты отвергнуты и по какой причине, что сломается, если сделать
иначе. Проект написан в этом стиле — посмотрите комментарии в `src/security.ts`
или `bin/typeorm-to-drizzle.sql`.

Номер issue — в описании: `Закрывает #941`.

## Проверки

На каждый PR запускаются четыре job'а из
[`.github/workflows/pull-request.yml`](.github/workflows/pull-request.yml), и все
четыре обязательны:

| Проверка | Что делает |
| --- | --- |
| Бэкенд — линтер, типы, тесты | Biome, `tsc` по двум конфигам, тесты против настоящей PostgreSQL, аудит прод-зависимостей |
| Фронтенд — тесты, типы, сборка | типы, vitest, сборка Vite, аудит прод-зависимостей |
| Раннер — исполнение 9 языков в Docker | собирает образы языков и реально прогоняет код, stdin, таймаут и изоляцию сети; проверяет, что контейнеры не осиротели |
| Сборка образов | образы бэкенда и фронтенда плюс `caddy validate` |

Проверок типов **две**: основная и `-p tsconfig.test.json`. Прогоняйте обе —
`npx tsc --noEmit && npx tsc --noEmit -p tsconfig.test.json`. Ошибка,
проходящая мимо первой, но валящая вторую, уже случалась.

Ветка обязана быть свежей относительно `main` (`strict`). Это не формальность:
при squash коммит в `main` не равен голове ветки, и без этого требования зелёный
PR проверял бы не то состояние, которое уедет в `main`. Если GitHub просит
обновить ветку — `git pull --rebase origin main`.

## Мерж — squash

Один PR — один коммит в `main` — одна запись в CHANGELOG.

Мерж-коммит и rebase не подходят: они уносят в `main` все внутренние коммиты
ветки, и release-please прочитает каждый. В CHANGELOG попадут `wip` и
`поправил опечатку` — так уже было, в закрытом релизном PR #948 всплыли записи
вида `header start` из старой истории.

Пока запрет остальных стратегий не настроен (см. issue #951), выбирайте **Squash
and merge** руками.

## Релиз

Теги руками не ставят, `make release` и `git push heroku` не существуют.

Версию считает [release-please](https://github.com/googleapis/release-please). На
каждый пуш в `main` он обновляет **релизный PR** с заголовком вида
`chore(main): release 0.2.1`: там поднятая версия в `package.json` и дописанный
`CHANGELOG.md`. Пока PR открыт, ничего не выпущено — он копит изменения.

**Мерж релизного PR и есть выпуск.** Один и тот же прогон:

1. ставит тег `v0.2.1` и создаёт запись в GitHub Releases;
2. публикует образы приложения, фронтенда и девяти раннеров в GHCR;
3. раскатывает оба стенда — свой сервер и PaaS.

Отсюда простое следствие: **частота выпусков — это частота, с которой мержат
релизный PR.** Хотите релиз на каждую фичу — мержите сразу; хотите раз в неделю —
он накопится за неделю и уедет одной версией.

### Версии до 1.0.0

Пока версия ниже `1.0.0`, `feat` поднимает patch, а не minor
(`bump-patch-for-minor-pre-major`) — так настроено в `hexlet-basics` и
`hexlet/hexlet`, и здесь сделано так же. То есть `0.2.1`, `0.2.2`, `0.2.3`, пока
кто-нибудь осознанно не выпустит `1.0.0`.

### Если раскатка упала

Тег и запись в Releases уже созданы — переделывать выпуск не нужно. Достаточно
перезапустить упавший job:

```bash
gh run rerun <id> --failed
```

Что делать, если не поднялся сам стенд, — в README, раздел
[«Развёртывание»](README.md#развёртывание). Отдельно учтите: на боевом стенде
откат кода в одиночку может не помочь, если выпуск нёс миграцию базы.

## Чего в этом процессе нет намеренно

**Обязательного ревью.** В репозитории один активный разработчик, и требование
ревью заблокировало бы его на собственных PR. Появятся ещё — включим.

**Проверки заголовка PR.** Сейчас ничто не мешает открыть PR с заголовком не по
конвенции, и такое изменение молча не попадёт в CHANGELOG. Это известная дыра,
она описана в issue #951 вместе с тем, чем её закрыть.

**Дублирования проверок на push в `main`.** `push.yml` делает меньше, чем
`pull-request.yml`, и это нормально: изменения приходят через PR, а строгость
нужна именно там.

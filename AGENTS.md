## Комментарий объясняет «почему»

Что делает код, видно из кода. В комментарий идёт то, чего не видно: какая альтернатива отвергнута и почему, какой сбой это предотвращает, что сломается, если сделать «очевидным» способом. Образцы — `src/security.ts` и `src/config/env.ts`: почти каждый комментарий там описывает поломку, которая уже случалась на боевом стенде.

Комментарии, сообщения коммитов и описания PR — на русском.

## Заголовок PR — это коммит в `main`

Мерж только squash (остальные стратегии отключены в настройках), поэтому заголовок PR остаётся в истории навсегда и по нему release-please считает версию и собирает CHANGELOG. Формат: `тип(подсистема): описание` — описание с маленькой буквы, без точки в конце.

Типов ровно шесть, они перечислены в `release-please-config.json`: `feat`, `fix`, `perf`, `revert`, `chore`, `build`. **Подсистема идёт в scope, а не в тип**: рефакторинг — `chore(runner):`, документация — `chore(docs):`, правка CI — `fix(ci):`. Заголовок с типом `docs:`, `ci:`, `refactor:`, `style:` или `test:` формально допустим по Conventional Commits, но проходит зелёным и молча выпадает из CHANGELOG и версии. Заголовки не проверяются (#951), так что это целиком на авторе.

Ветка — от `main`, имя вида `fix/database-ssl`. Коммиты внутри ветки в `main` не попадут: squash сворачивает их в заголовок PR.

Описание PR пишут для того, кто придёт читать код позже: какую проблему решали, какие варианты отвергли, что проверено и как.

## Перед пушем

```bash
npm run lint && npx tsc --noEmit && npx tsc --noEmit -p tsconfig.test.json && npm test
```

Проверок типов две: основная и `-p tsconfig.test.json`. Основной конфиг исключает `*.test.ts`, и ошибка, проходящая мимо первой проверки и валящая вторую, уже случалась (#945).

`npm test` — это юниты раннера (Docker не нужен) плюс jest, которому нужна живая PostgreSQL: `docker compose up -d db`. Фронтенд проверяется отдельно, из `frontend/`: `npx tsc --noEmit && npm test`.

Ветка обязана быть свежей относительно `main` — `git pull --rebase origin main`.

## После правки `src/` — перегенерировать типы для фронтенда

```bash
npm run generate:types
```

Фронтенд берёт тип роутера из `types/`. Без этого шага он проверяет типы против устаревшего слепка — и проверка проходит, потому что проверять нечего.

## После правки схемы — сгенерировать и закоммитить миграцию

```bash
npm run db:generate
```

Файл появляется в `drizzle/` и версионируется вместе с кодом; приложение применяет миграции само при старте. Почему генерировать их в сборке или в CI нельзя — в [README, «Миграции базы данных»](README.md#миграции-базы-данных).

## Выпуск — это мерж релизного PR

Теги руками не ставят, `make release` не существует. Версию считает release-please: он держит открытым PR `chore(main): release X.Y.Z`, и мерж этого PR и есть выпуск — тег, образы в GHCR, раскатка обоих стендов. Подробности — в [docs/deployment.md](docs/deployment.md).
